# FORMOS-ARCH-FIX-002 — Validation Boundary Finalization & Architecture Freeze

**Date:** 2026-10-28 · **Scope:** one boundary only (Zod vs SECURITY DEFINER RPC). No redesign, no new infrastructure, no scope change, no implementation. Method: full-text audit of `docs/arch/` for execution-boundary wording (`read`/`grep`); no new external research needed (RJSF v6.11.0 evidence already captured in FIX-001).

## 1. Issue
FIX-001 language stated "Zod is the sole validation authority client + server" alongside "anonymous intake is exclusively through a hardened PostgreSQL SECURITY DEFINER RPC," with sentences implying the server "re-derives Zod … inside the intake RPC." A PostgreSQL/PL/pgSQL function cannot execute the TypeScript/Zod validator generated by application code — so the two statements, read literally, demanded an impossibility. Left unresolved, implementers would split into two incompatible models (Zod-in-RPC vs Zod-never-near-RPC) or, worse, "resolve" it by moving submission writes into a service-role API route and deleting the RPC boundary.

## 2. Decision
Two layers, fixed order, one writer. **Layer 1 — API/BFF (TypeScript):** publication lookup, captcha/abuse/rate-limit, then generated Zod validation re-derived from the pinned `publishedVersion` snapshot (same generator as the client); field failures → 422 with zero DB touch and no RPC call. **Layer 2 — intake RPC (PL/pgSQL, SECURITY DEFINER):** the ONLY database writer for anonymous submissions; enforces in-transaction invariants (publication active/schedule, workspace-from-publication, caps, unique, idempotency, attachment-ref integrity, outbox atomicity, no SELECT-back) plus defensive shape/type checks as an integrity floor — and NEVER executes Zod. The RPC is not exposed to `anon`/`authenticated` (no EXECUTE grant), so Zod cannot be bypassed by direct invocation; the API route calls it via a least-privilege `intake_caller` role (EXECUTE-only, zero table grants — never service-role in the request path). This preserves both principles untouched: Zod remains the sole *application/schema* authority, the RPC remains the sole *database write* authority.

## 4. Canonical Anonymous Submission Flow
```text
Anonymous Browser
      ↓
Public Intake API / BFF (TypeScript)
      ↓
publication lookup / redacted metadata
      ↓
CAPTCHA / abuse / rate limiting (BEFORE any DB write)
      ↓
server-side generated Zod validation (pinned publishedVersion; 422 = stop, no RPC)
      ↓
SECURITY DEFINER submission RPC (least-privilege intake_caller EXECUTE-only)
      ↓
Postgres transaction
      ├── submission
      ├── submission field/index materialization
      ├── attachment references (pre-scanned refs only)
      └── outbox event
      ↓
receipt-only response (no SELECT-back)
```

## 5. Security Invariants (what the RPC guarantees even if Layer 1 were bypassed)
Publication exists + active + schedule-open (re-checked in-txn, not trusted from Layer 1) · `workspace_id` derived from the publication row; caller-supplied workspace values ignored + logged-and-rejected · caps, unique-field (advisory-locked), and 24h idempotency enforced in-txn · attachment refs exist, scanned-clean, session-bound · defensive shape/type floor (NOT NULL, length caps, FK existence) with 500-class integrity rejection + alert on violation · atomic submission+index+refs+outbox commit · receipt-only return. Anon role: `SELECT` → redacted-publication-metadata path only; `INSERT/UPDATE/DELETE` → DENIED (no table grants, no EXECUTE grant). This set is invariant text: SUBMISSION-PIPELINE.md §Authorization boundary is the normative reference.
